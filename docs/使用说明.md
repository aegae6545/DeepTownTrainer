# 深城（Deep Town）修改器 · 使用说明

> 适用版本：深城 5.7.8（com.rockbite.deeptown，versionCode 398）
> 适用环境：MuMu 模拟器 12（ADB root），PC 端 Windows
> 更新：2026-10-10（v4）

---

## 一、快速上手

0. **认版本：窗口标题栏写着 `深城修改器 v5`** —— 如果标题不是 v5，说明你开的是旧进程：
   先关掉旧窗口（或任务管理器里结束 `pythonw.exe`），再重新双击 `启动修改器.bat`。
   主界面底部应显示「共 350 项」，第二行有「⏱ 倒计时 / 立即完成」「🧩 机制杀助手」，左上角「🔄 重启辅助」。
1. **启动模拟器，打开深城**，进入游戏主界面
2. **双击 `启动修改器.bat`** —— 左上角显示 `● 已连接` 即成功
3. 点 **「🔌 连接智能通道（Frida）」** —— 变成绿色 `● 已连接`（推荐，一次就够）
4. 搜索框输入要改的东西（如 `金币`），**双击列表项**，**只填「改成多少」** → 点「一键修改」

> 第一次用智能通道会往模拟器里推一个 frida-server（约 110MB，一次性），需要十几秒。

**改完点主界面「强制保存进度」**，让游戏把新数值写进存档。

## 二、v5 新增（2026-10-12）

| 你反馈的问题 | 根因 | 现在 |
|---|---|---|
| **街区打不动伤害（铁长老 / 熔岩岩块 / 铝长老）** | 这些街区**不吃伤害是设计**：伤害 = `原始伤害 × 街区.getHitMod()`，而这些街区的 `getHitMod()` **恒返回 0**。实测 `u4.i`（铁长老 IRONBOSS）`getHitMod()=0`、免疫表空；`u4.j`（熔岩岩块 LavaBlock）未冻结时也返回 0；`u4.a`（铝长老）同样恒 0。**DPS 拉多高都是 ×0**，连 `BLOCK_HIT` 事件都不会发 | 主界面新增 **「🧩 机制杀助手」**：① 只读检测当前街区是什么、需要什么机制、前置状态；② **一键完成前置条件**（按类型分派，见下）；③ **逐条列出做了什么** |

### 机制杀助手做了什么（按类型）

| 街区 | 机制 | 助手执行的动作 |
|---|---|---|
| `u4.j` **熔岩岩块** | 需要技术研究所（建在**上一段**）+ 低温冷冻（耗 1 液态氮） | 直接调游戏自己的 `freeze()`：写入冻结标记 `LAVA_BLOCK_FROZEN=true` + 清空免疫表（`ice-cannon`/`miracle-gas`/`fire-cannon`） |
| `u4.i` **铁长老** | **终局剧情杀**。光造火箭（`rocket-base-*`）不够 —— 必须先建齐 **信号接收器 / 研究建筑 / 银河传送门** 三栋建筑（都 `unlockSegment=108`），`a5.e` 系统才会启动，走完发射剧情后由 `a5.e$a0 → B0 → S0 → u4.i.A()` 把它杀掉 | ① 面板**列出终局前置清单**（三栋建筑建了没 + 三件套材料有多少）；② **「🎁 补齐终局材料」**把 `receiver-skeleton` / `radar` / `portal-for-mankind` 各 1 塞进仓库；③ **不能用伤害杀** —— 它是地球最底层街区（row 1079），打碎后背景渲染器 `r4.b.d()` 取不到下一层的 `bgWall` 纹理 → GLThread NPE 闪退（已实测两次）。想硬来只能用「⚠ 强制旁路」，风险自负 |
| `u4.a` **铝长老** | 剧情设计上就是「打不动、绕开它」 | 旁路：`getHitMod()` 强制 1.0 + 免疫表清空 |
| 其它 `getHitMod()==0` | 未知机制 | 兜底旁路（同上） |

- 旁路**不随面板关闭撤销**（你要关掉面板回游戏打它）；主界面会显示 `机制旁路：● 开`
- 想撤掉：面板里点 **「↩ 撤销旁路」**，或重启游戏 / 断开智能通道（钩子随 frida 会话结束自动失效）
- 旁路生效期间，**所有**街区的 `hitMod` 都按 1.0 算 —— 普通街区本来就是 1.0，BOSS 原本有减免（如第 9 区域 0.17），会被一并拉满

#### ⚠ 闪退已修（2026-10-12 晚）

第一次做出来的「一键完成」在铁长老上**会闪退**。崩溃报告（`/data/system/dropbox/data_app_crash@…14:45`）：

```
java.lang.NullPointerException: Attempt to write to field 'boolean z6.a.d' on a null object reference
    at z6.b.b          ← z6.b.b() = pool.obtain(); obj.d = false;   obtain() 吐了 null
    at z6.a.d → z6.a.w → r4.c.i → r4.i.F → r4.a.F → r4.a.g → r4.i.l → r4.i.U → i5.v（法术）
```

**根因**：铁长老 `getHitMod()` 恒 0，所以游戏里 `伤害 = dmg × 0` → `if (伤害 > 0)` 永远为假 →
`r4.i.l()`（伤害结算）**从来没被执行过**。旁路把 `hitMod` 拉成 1.0 后这条路径第一次被打开，
踩到游戏自己的 bug：`z6.b`（大数对象池，libGDX `Pool` 单例）的 `obtain()` 偶尔返回 `null`，
紧跟的 `iput-boolean` 直接 NPE。

**修法**：旁路开启前先装 **大数池护栏** —— hook `z6.b.b()`，拿不到就 `new z6.a()` 兜底
（构造后 `d` 默认 false，与原方法语义一致）。护栏只在旁路开启期间生效，撤旁路时一并撤掉。
主界面/面板会显示 `池护栏` 状态与兜底次数。

**第二次崩溃（15:04，杀死 boss 的瞬间）** —— 换了个地方，池护栏也救不了：

```
java.lang.NullPointerException: 'int c0.q.b()' on a null object reference
    at r4.b.d        ← 对 null 的 TextureRegion 调 .b()
    at r4.j.l ← r4.b.c ← m5.h.c ← m5.k.r/t/s ← t.h.render ← onDrawFrame(GLThread)
```

`r4.b.d(row)` 是**矿区背景渲染器**，要拿该行所在区域的 `bgWall` 纹理：
`res.getTextureRegion( q(y).bgWall )` → 返回 null → `v7.b()` NPE。

铁长老在**地球最底层 row 1079**。打碎它之后，背景要往下多画一层，那一层的纹理取不到 → 渲染线程直接崩。
**这是游戏自身的硬限制：最底层街区不能用伤害打碎。** 所以：

- `mechFix` **不再自动装旁路**，只做安全动作（熔岩→`freeze()`；铁长老→报清单 + 自动补材料）
- 旁路挪到独立按钮 **「⚠ 强制旁路（可能闪退）」**，点了会弹二次确认
- 好消息：这次崩溃**没有写坏存档**（重启后铁长老 HP 满、`hitMod=0`，一切如常）

#### 铁长老正解：**存档级一键完成**（2026-10-12 晚，推荐）

反汇编确认了游戏自己走完终局时调的就是这一串（`a5.e$e0.run()` → `a5.e.F0()` → **`a5.e.O0()`**）：

```java
a5.e.O0() {
    game.q.t("research_building_group");                    // 开任务组
    game.n.v5("research_building");                         // 解锁功能
    game.n.v5("galactic_portal_building");
    game.n.x("radar");                                      // 解锁建筑
    prefs.v("GALACTIC_MOVIE_SUCCEED_DONE", "true");          // ← 写存档
    prefs.s();                                              // 存盘
}
```

而铁长老「已击败」的判定就是读这个键：

```
u4.i.init(I)  → game.n.w0("GALACTIC_MOVIE_SUCCEED_DONE") → 真则 P = true
h4.d.w0(k)    → Boolean.parseBoolean( SaveData.bulkConfig.get(k) )
j4.b.v(k, v)  → SaveData.bulkConfig.put(k, v); s()        ← 官方写入路径
```

⇒ **面板点「✅ 一键完成前置条件」就等于把终局前置在存档里做完了**：调一次 `O0()`，再把
`bulkConfig["GALACTIC_MOVIE_SUCCEED_DONE"] = "true"` 复写一遍兜底，并把当前铁长老的 `P` 置 true。

**实测**：执行后 `bulkConfig` 出现 `GALACTIC_MOVIE_SUCCEED_DONE = true`；
**重启游戏后标记仍在**，铁长老 `P = true`（血条消失）—— 存档级生效 ✔

> 代价：原本的发射剧情 / 结局动画被跳过（面板会先弹确认框）。
> 那三栋建筑不用再建了 —— 面板列出来只是给你看游戏原本的路径。

#### 铁长老原本的路径（仅供参考，已不需要走）

| 终局前置 | 造价 | 部署 |
|---|---|---|
| **信号接收器** `receiver_building` | `receiver-skeleton`×1（铜钉1000+钛齿轮100+钢板100，手工车间 1h） | 8h |
| **研究建筑** `research_building` | `radar`×1（磁铁15+光纤200+主板20，3h） | 8h |
| **银河传送门** `galactic_portal_building` | `portal-for-mankind`×1（传送门骨架1+大脑1+纳米锤1） | 12h |

三栋都建好后走发射剧情，结束时会写标记 `GALACTIC_MOVIE_SUCCEED_DONE`。
**材料可以让面板一键塞（「🎁 补齐终局材料」），建筑必须你自己在矿里放**；
放好后用 **「⏱ 倒计时 / 立即完成」** 把 8h/8h/12h 的部署时间归零。

## 二·旧、v4 新增（2026-10-10）

| 你反馈的问题 | 根因 | 现在 |
|---|---|---|
| 「远征」调 20 倍变速，倒计时速率没变 | 远征/生产倒计时**不走游戏帧时间（deltaTime），走的是墙钟**。调度器 `a7.b` 里存的是绝对结束时间 `endTime = System.currentTimeMillis()/1000 + 时长`，界面上那个 `00:02:00` = `endTime − 当前墙钟`。放大 deltaTime 动不了墙钟，所以倍数调到多少都没用 | 新增 **「⚡ 远征 / 立即完成」面板**：一键把 `endTime` 挪到"现在"（等价于倒计时走完），另有**真实生效的远征加速**（按倍率改写 endTime） |
| 想要"远征立即完成" | — | 见第六节：可只「立即完成」，也可「完成并领取奖励」一步到位 |
| **变速把游戏冻住 / 有时完全没效果** | 原实现是「钩 `AndroidGraphics.onDrawFrame` + 回拨 `lastFrameTime`」。2026-10-10 实测确认：**在本环境（frida 16.7.19 + MuMu12/ART）里，替换体中的 `this.onDrawFrame(gl)` 根本不会调到原方法**，而是再进一次替换体、原方法永不执行 ⇒ 渲染停摆（deltaTime 冻结、`gameplayTime` 3 秒推进 0.000）。连"空钩子"都会冻住游戏；它也是 14:34 那次 GL 线程栈溢出崩溃的元凶 | 变速改成**只放大 `Ashley Engine.update(dt)`**：确定性生效，不再依赖猜混淆字段（顺带干掉 `if (lv>1e12)` 那个"模拟器刚重启就失效"的老坑）；另外给广告钩子统一加了递归深度护栏 |
| **工艺制作的进度条不会被变速加快**（只有动画变快） | 和远征同一个原因：制作/冶炼的计时也是 `universalScheduler` 里的**绝对墙钟 endTime**（key = `<建筑uID>recipie_<槽位>`），不是帧时间 | 面板从「远征」扩成**「⏱ 倒计时」**：把制作 / 冶炼 / 远征 / 建筑部署 / 商店冷却**全部**列出来，可以「立即完成」或按倍率「加速」（默认只作用于「生产/制作」筛选） |
| **变速突然不生效**，面板日志刷「⚠ 找不到 lastFrameTime 字段」 | 字段识别里写死了一句 `if (lv > 1e12)`。`System.nanoTime()` 是**单调时钟**（从模拟器/容器启动算起），刚重启的模拟器只有 ~3e11 —— `lastFrameTime` 被这个阈值直接挡掉 | 整条「猜字段」的路已经废掉，变速改为直接放大 `Engine.update(dt)`（不再需要识别任何混淆字段） |
| 想要 UI 上的「重启辅助」 | 广告屏蔽 / 变速 / 远征加速都是**运行时钩子**，游戏一重启就全丢 | 主界面新增 **「🔄 重启辅助」**：重启游戏 → 等进程起来 → 自动重连智能通道 → **原样挂回**广告屏蔽 / 变速 / 远征加速（见第七节） |

## 四、两种工作方式

| | 智能模式（推荐） | 手动模式 |
|---|---|---|
| 依赖 | 需要 Frida 通道 | 不需要，纯 ADB 内存扫描 |
| 你要填什么 | **只填目标值** | 要填"游戏里现在是多少" + 目标值 |
| 当前值从哪来 | **工具自己读出来并显示** | 你自己照抄游戏界面 |
| 看不见的字段 | ✅ 能改 | ❌ 改不了 |
| 可中止 | 秒级 | 有 ■ 停止 按钮 |

**智能模式解决的就是"我根本看不到这个值是多少"** —— 工具直接连进游戏的 Java 对象，
把字段的当前值读出来显示给你，你只管填目标值。

> 手动模式如果提示"候选过多，需要再确认一步"：回游戏让这个数值变一点点，
> 回来把①改成新数字，再点「继续修改」。这是两步收敛法。

## 五、游戏变速（全局时间流逝）

主界面点 **「游戏变速（时间流速）」**。

| 项 | 说明 |
|---|---|
| 可调范围 | 0.05x ~ 20x（预设 0.1/0.25/0.5/1/2/3/5/10/20，也可自定义） |
| **生效范围** | 采矿 / 生产 / 机器人 / 动画 / 动作 —— 一切走游戏帧逻辑（Ashley ECS）的东西 |
| **不生效** | 商店冷却、每日礼物、**制作进度、远征倒计时**这类按**墙钟**算的计时（要快请用第六节的倒计时面板） |
| 原理 | 钩 `com.badlogic.ashley.core.e.p(float)`（Ashley 的 `Engine.update(deltaTime)`，每秒 60 次），把 dt 乘倍率再转交原方法 —— 所有 ECS 系统拿到的就是放大后的时间片 |
| 状态行 | `ECS 时间片 a→b`：a 是游戏给的原始 dt，b 是转交出去的。10x 时 b ≈ 10×a |
| 持久性 | 运行时钩子，**游戏重启后失效**，重新点「应用」即可（或点「🔄 重启辅助」自动恢复） |

**实测证据（2026-10-10 改完之后）**：钩住 Ashley 系统基类 `com.badlogic.ashley.core.i.update(float)`
看它实际收到的 dt，同时用 `SaveData.gameplayTime` 确认游戏没被冻住：

```
1x  : ECS 时间片 0.0191 -> 0.0191   系统收到 0.0158 ~ 0.0344   gameplayTime 3 秒推进 2.961 秒 ✔
10x : ECS 时间片 0.0169 -> 0.1693   系统收到 0.1636 ~ 0.1721   gameplayTime 3 秒推进 2.965 秒 ✔
还原: ECS 时间片 0.0207 -> 0.0207                             gameplayTime 3 秒推进 2.973 秒 ✔
```

（`gameplayTime` 不跟着加速是**正常的**：它不是 ECS 累加器，读的是没被放大的
`Gdx.graphics.getDeltaTime()`；真正在玩的采矿/生产/机器人/动画全在 ECS 里，都拿到了放大 10 倍的时间片。）

**旧实现的历史实测**（钩 `Engine.update` 看 dt）——

```
1x  : 0.016594, 0.030489, 0.003027, 0.018509, 0.016258 ...   ← 真实帧间隔
10x : 0.015443, 0.016697, 0.300000, 0.035768, 0.178090, 0.163622, 0.165971 ...   ← 约 10 倍
30x : 0.300000, 0.300000, 0.300000 ...                        ← 被 0.3 上限夹住
```

## 六、倒计时：制作 / 远征 / 部署（立即完成 + 加速）

主界面点 **「⏱ 倒计时 / 立即完成」**，或双击列表里的「倒计时：制作 / 远征 立即完成」。

**先说结论：制作进度、远征倒计时都不吃「游戏变速」。** 变速改的是游戏每帧的时间片（deltaTime），
而这些计时的剩余时间是**墙钟** —— 深城里所有"要等"的计时都塞在同一个调度器里：

```
SaveData.universalScheduler  (类 a7.b)
   c:double = System.currentTimeMillis() / 1000      ← 当前墙钟秒
   任务 a7/b$b:  endTime = 创建时的墙钟秒 + 时长      ← 绝对结束时间(存档里存的就是它)
   i(key)   = endTime - 当前墙钟                      ← 界面上那个 00:02:00
```

实测任务表：

| key 形式 | 是什么 | 回调 |
|---|---|---|
| `<建筑uID>recipie_<槽位>` | **制作 / 冶炼 / 化工**的每一格生产 | CraftingBuildingScript 等 |
| `<建筑uID>start-expedition` | 远征 | CaveExpeditionBuildingScript |
| `<建筑uID>deploy` | 建筑部署 | logic.building.a |
| `boost<uID>` / `boost_*_cooldown_key` | 增益 / 加成报价 | — |
| `bot_system_action_timer_N` | 机器人动作 | — |
| `*_mini_offer_cooldown_key` / `FREE_COINS_COOLDOWN_NAME` / `special_pack` | 商店 / 礼包冷却 | — |

所以把 deltaTime 放大 20 倍，墙钟一秒还是一秒，进度条和倒计时纹丝不动 ——
**只有动画（帧驱动）会变快**。这就是"工艺制作只加快动画、不加快制作时间"的原因。
（实测：变速开到 10x 时 `Engine.update` 收到的 dt 从 0.0165 变 0.165，但制作/远征剩余时间照旧 1 秒 1 秒地掉。）

面板用法：

1. **筛选**（默认「生产/制作」）：生产/制作 · 远征 · 建筑部署 · 增益/加速 · 机器人 · 商店/礼包 · 全部
2. 表格列出该筛选下所有计时（类别 / 目标 / 剩余 / 结束时间）

| 按钮 | 干了什么 | 会不会动存档 |
|---|---|---|
| **⚡ 立即完成（当前筛选）** | 对该筛选下每个计时调 `a7.b.r(key, 0)`，把 `endTime` 直接改成"现在"。下一帧游戏自己的调度器判定到期 → 回调 → 制作完成 / 远征完成，任务自动移除 | 会（等于计时走完了） |
| **⚡ 立即完成（选中）** | 只处理列表里选中的那一行 | 会 |
| **🎁 领取远征奖励** | 先完成远征，0.7 秒后再走一遍游戏自己的"领取"入口（`ExpeditionBuildingScript.b1()`），直接把奖励收进收藏 | 会 |
| **加速 xN（作用于当前筛选）** | 每 250ms 按倍率把 `endTime` 往前推（游戏自己的生产建筑就是这么做时间加速的），**真实生效**，与全局变速无关 | 会 |

**加速实测**：把筛选设成「生产/制作」、倍率 10x，看某个制作任务的剩余时间 ——
每 0.5 秒掉 5.0~5.1 秒，也就是 **10.1 秒/秒 = 10x** ✔（不做任何加速时是 0.5 秒/0.5 秒）。

> 「立即完成」走的是**游戏自己的到期路径**，不是往存档里硬塞状态 —— 所以奖励、下一段远征的解锁、
> 存档写入都和正常等完计时一模一样。实测领取后 `SaveData.explorables` 里确实多出了对应收藏品。
>
> 加速是运行时行为，**游戏重启后失效**（面板关掉也会自动停）。远征的 `endTime` 存在存档里，
> 即使中途关游戏，倒计时也会按墙钟继续走 —— 这是游戏原本的机制。

## 七、重启辅助（重启游戏 + 自动恢复所有辅助）

主界面左上角 **「🔄 重启辅助」**。

广告屏蔽、游戏变速、远征加速都是**运行时钩子**，游戏一重启就全没了 —— 以前每次都要
「重新连接 → 连智能通道 → 开广告 → 设变速」点四遍。这个按钮一次搞定：

```
① 记录当前辅助状态（广告开关 / 变速倍率 / 远征加速倍率）
② 断开 Frida 通道（游戏重启会带走会话）
③ am force-stop 结束游戏
④ 重新拉起游戏
⑤ 等进程起来（最多 90 秒）
⑥ 等 10 秒让引擎开始出帧
⑦ 重连 Frida 智能通道
⑧⑨⑩ 原样挂回 广告屏蔽 / 变速 / 远征加速
```

全过程日志会实时打在弹窗里。实测：5x 变速 + 广告全开 + 50x 远征加速 →
点一下按钮 → 游戏 pid 变化（真的重启了）→ 三项钩子全部自动恢复（`deltaTime` 回到 5 倍）。

> 如果连智能通道没连上，会先问你要不要"只重启游戏（不自动恢复）"。

## 十四、逆向原理（写给想深入的人）

### 1. 货币防作弊机制（i4/a、i4/b 类，classes5.dex）

```
i4/b {long b, long c, Object d}   ← 金币（long 版）
i4/a {int  b, int  c, Object d}   ← 钻石 / 资源数量（int 版）

f():  c = c - b;  if (c<0) c = 0         # 归一化出真实值
g():  b = rand(-50000, 50000); c = c + b # 每次读取重新随机偏移
h():  f(); g(); return c - b             # 对外返回的真实值
```

⇒ 内存里**没有任何位置直接等于金币数**，真实值 = `c - b`。修改：写 `b = 0, c = 目标值`。

### 2. 存档对象 SaveData（未混淆，classes4.dex）

`com.underwater.demolisher.data.vo.SaveData`，**135 个字段，全局单例**，
字段名全部未混淆（`cash` / `crystals` / `currentLevel` / `spellPoints` /
`shopFreeCoinsRewardedCount` / `materials` / `mineData` …）。

- `cash` → `i4.b` 实例；`crystals` → `i4.a` 实例
- `materials` → `HashMap<String, i4.a>`，key 是资源英文名（`coal` / `copper` / …）
- **嵌套字段**：`mineData.currentSegment`（`MineData` 里，`EarthMineData` 继承）
  ⇒ 反射找字段必须**沿继承链**走 `getSuperclass()`，`getDeclaredField` 不查父类

**这是智能模式的全部秘密**：`Java.choose('…SaveData')` 拿实例 + 反射按名读写，
完全不需要知道当前值。

### 3. 游戏时间源（2026-10-08 实测）

查了一圈，结论有点反直觉：

| 候选 | 实测结果 |
|---|---|
| `Graphics.getDeltaTime()`（`AndroidGraphics.e()`） | **每秒 60 帧在渲染（`onDrawFrame` 300 次/5s），但 getter 被调用 0 次** → 调用点被 ART 内联了，钩 getter 永远钩不到 |
| `System.nanoTime()` | 5 秒 14 次，很少。**⚠ 千万不要 hook 它** —— ART 内部也用，替换会让游戏直接崩溃（实测踩过） |
| `System.currentTimeMillis()` | 5 秒 26 次；游戏侧只有 `x6.g0.b()`（**日期函数**：`(millis+时区)/86400000` = 第几天）和任务系统在读 |
| `com.badlogic.ashley.core.e.p(float)` | **每秒 60 次，dt ≈ 0.0167** ← 这才是游戏逻辑的真正入口 |

⇒ 变速的正确做法：钩 `AndroidGraphics.onDrawFrame`，在调用原方法**之前**
把 `lastFrameTime` 回拨，让原方法自己算出的 `deltaTime` 就是放大后的值。
这样连被内联的 getter 也躲不掉（它读的就是那个字段），`Engine.update` 拿到的 dt 也一起放大。

AndroidGraphics 实测字段：`p:float = deltaTime`、`o:long = lastFrameTime`
（字段名随混淆会变，所以运行时按"值特征"自动识别：float 里最接近 `getDeltaTime()` 的、
long 里最接近 `System.nanoTime()` 的）。

> ⚠ **踩过的坑（2026-10-10）**：早期版本识别 long 字段时写了 `if (lv > 1e12)`。
> `System.nanoTime()` 是**单调时钟**，不是 epoch —— 模拟器刚重启时只有 ~3e11，
> 于是 `lastFrameTime` 被判掉，变速报「找不到 lastFrameTime 字段」直接失效。
> 判定必须用"与 nanoTime 的距离"，不能设绝对量级门槛。现在改成 `|nanoTime - v|` 最小且 `< 1e9`，
> 再加 `Engine.update(dt)` 兜底。

### 4. 技能冷却（SpellData，未混淆）

```
 -8  String ref  -> 法术名（如 "fire-cannon"）   ← 定位钥匙
 -4  ref
 +0  int   cost
 +4  int   unlock_level
 +8  int   unlock_level（同值副本）
+12  float cooldown          ← 改写目标
```

定位：搜法术名字符串 → 找"哪个字段引用了它" → 该字段 +8 即 cost、+12 即冷却；
再用 `(cost, unlock, unlock, cooldown)` 四元组校验。

### 5. 广告链路（AppLovin MAX）

| 类 | 作用 |
|---|---|
| `com.applovin.mediation.ads.MaxInterstitialAd` | 插屏 |
| `com.applovin.mediation.ads.MaxRewardedAd` | 激励视频 |
| `com.applovin.mediation.MaxAdListener` | `onAdLoaded/Displayed/Hidden` |
| `com.applovin.mediation.MaxRewardedAdListener` | `onRewardedVideoStarted/onUserRewarded/onRewardedVideoCompleted` |
| `com.applovin.impl.mediation.ads.MaxFullscreenAdImpl` | SDK 内部实现，`listenerWrapper` 是包着游戏监听器的代理 |
| `s3.a$e`（混淆） | **游戏自己的监听器**，真正发奖的地方 |

**关键点**：`s3.a$e.onUserRewarded` → `a(MaxAd)` 里算 `dt = (now - b) / 1000`，
只有 **`dt > 10` 秒**才发奖（`b` 在 `onRewardedVideoStarted` 里被设成当前时间）。

做法：① 钩 `MaxRewardedAd.showAd`（所有重载）不展示真实广告 →
② 把 `s3.a$e.b` **回拨 60 秒** → ③ 依次触发 5 个回调。

⚠ MAX 的 `listenerWrapper` **不接受 `null` 参数**（内部会 `ad.getAdUnitId()` 抛 NPE），
所以是**直接驱动游戏自己的 `s3.a$e` 监听器**，不走 SDK 包装层。

### 6. 引擎性能

- 设备端 `dd ... | gzip -1` 压缩回传 + numpy 本地匹配：
  1.2GB Java 堆快照约 **1.8 秒**
- **类指针批量读**：`strict_filter` 原来对每个候选调一次 adb（每个 ~9ms），
  现在从快照里用 numpy 批量 gather 4 字节，**零 adb 往返**，2 万候选 72s → 4.5s
- Windows 上所有 `adb.exe` 调用都加了 `CREATE_NO_WINDOW + SW_HIDE`：不再弹窗抢前台

### 7. 远征 / 生产倒计时 = 墙钟，不是帧时间（2026-10-10 实测）

```
SaveData.universalScheduler : a7.b          ← 通用调度器（一个就够全局用）
    b:double  cursorTime    游戏内游标(秒)
    c:double  wallNow       System.currentTimeMillis() / 1000   ← 真墙钟
    f:HashMap<String, a7/b$b>  任务表
    a7/b$b { b:String key, c:double endTime, d:a7.a 回调 }
    b(String key,int 秒,a7.a 回调)  创建任务: endTime = b + 秒
    i(String key):float   = endTime - wallNow      ← 界面倒计时就是它
    r(String key,float v) = endTime += v - i(key)  ← 改剩余时间(游戏自己加速生产建筑就用它)
    p(String key)         移除任务
    f(String key)         立刻触发回调 + 移除任务
    w(float dt)           每帧 tick: b += dt; c = 墙钟; 追赶到期 -> m() -> n()
    n()                   到期任务: 调回调 -> 从表里移除
```

- 任务 key 一览（2026-10-10 实测 23 个任务）：
  `<建筑uID>recipie_<槽位>`（制作/冶炼，回调 `CraftingBuildingScript`/`SmeltingBuildingScript`）、
  `<建筑uID>start-expedition`（远征，回调 `CaveExpeditionBuildingScript`）、
  `<建筑uID>deploy`（建筑部署）、`boost<uID>` / `boost_*_cooldown_key`（增益）、
  `bot_system_action_timer_N`（机器人）、`*_mini_offer_cooldown_key` / `FREE_COINS_COOLDOWN_NAME` /
  `special_pack` / `OFFLINE_RAIN_KEY`（商店冷却）
- 远征任务 `key = <建筑 uID> + "start-expedition"`，回调就是 `CaveExpeditionBuildingScript`
  （它 implements `a7.a`，`b(id)` 里 `id == j1()` 就调 `c1()` 完成远征）
- **⇒ 倒计时是绝对墙钟时间，放大 deltaTime 对它无效** —— 这就是"调 20 倍没变"的根因
- 「立即完成」= `r(key, 0)`：把 endTime 挪到"现在"，下一帧游戏自己判定到期 → 回调 → 完成 + 移除任务
- 游戏自己的时间加速也是同一套 API：`RecipeBuildingScript.B1(F)` → `a7.b.r(key, F)`；
  `ObservatoryBuildingScript.k1()` → `a7.b.f(key)`
- 远征奖励的落库位置：`SaveData.explorables`（Array<String>，收藏品 id 列表）
- 远征进度存在 `BuildingVO.progressDataDOM`（Json），字段只有 `isInProgress / itemToClaim / expeditionId / order`
  —— **没有时间戳**，时间戳只在调度器里

### 8. 机制杀街区 = getHitMod() 返回 0（2026-10-12 实测）

伤害结算入口（`r4.i.b(z6/a,F,F,F,F)` / `r4.i.U(...)`）：

```java
hitMod = 当前街区.getHitMod();
伤害   = dmg * hitMod;                       // z6/a 大数乘法
if (伤害.toFloat() > 0) { l(...); 触发 "BLOCK_HIT"; }
// 否则整段跳过 —— 连事件都不发
```

所以「打不动」= 街区的 `getHitMod()` 返回 0，与 DPS 无关。

| 类 | 街区 | `getHitMod()` 行为 | 正解机制 |
|---|---|---|---|
| `u4.j` | 熔岩岩块 LavaBlock | `c(row)` 为假 → 强制 `return 0`（内部 `hitMod` 字段其实是 1.0） | 技术研究所（**上一段**）+ 低温冷冻（耗 1 液态氮）→ `freeze()` |
| `u4.i` | 铁长老 IRON_BOSS（`getType()=IRONBOSS`，地球最底 row 1079） | 恒 `return 0`，免疫表为空 | 造完整枚火箭 + 发射剧情 → `a5.e$a0.run()` → `S0()` → `u4.i.A()` |
| `u4.a` | 铝长老 ALUMINIUM_BOSS | 恒 `return 0`，免疫 `mining-laser`/`fire-cannon`… | 剧情设计上打不动（对话提示「离开它」） |

**LavaBlock 的冻结链**：

```
u4.j.getHitMod()  =  c(row) ? hitMod(字段) : 0
u4.j.c(row)       =  prefs.e("LAVA_BLOCK_FROZEN")  &&  d(row)
u4.j.d(row)       =  (row == r4.i.x())            ← 必须是「当前正在挖的那一格」
u4.j.freeze()     =  prefs.v("LAVA_BLOCK_FROZEN","true") + spellImmunityList.clear()
u4.j.destroy()    =  prefs.v("LAVA_BLOCK_FROZEN","false")   ← 打碎一块就复位, 下一块要再冻
u4.j.getSpellImmunityList() 未冻结时塞入 ice-cannon / miracle-gas / fire-cannon
```

- 区域号 = `row / 108`（108 = 12 段 × 9 行）；`planet_config.xml` 里 `zone id="test9"` 是 `blockType="lava"` ⇒ **第 9 区域（row 864~971）整片熔岩，每块都要单独冻**
- 技术研究所的段位要求：`CryoFreezeScript.c()` 把要求段设为 `r4.i.A() - 1`（当前段 − 1），文案 `TEXT_TECH_LAB_POSITION_REQUIREMENT=低温冷冻要求技术研究处于熔岩岩块正上方。`
- 大数显示：`z6.a` = `float b` + 数量级下标 `c`，单位表 `["","K","M","B","T","q","Q","s","S","O","N","d","U","D"]`，每级 ×1000 ⇒ **`46 s` = 4.62×10²²，不是 46 秒**

**铁长老的击败链**：`a5.e`（ECS 系统，持 `ReceiverBuildingScript`）→ `a5.e$y.run()` → `u0()` → `U0()` → `u4.i.D()`；
`a5.e$a0.run()` → `B0()` → `S0()` → `u4.i.A()`（`P` 标记置位 + `death` 动画 + `z5.v0.R()`）。
`u4.i.init()` 里若 `prefs("GALACTIC_MOVIE_SUCCEED_DONE")` 已存在则直接 `P=true`（即已通关）。

### 9. 大数对象池 z6.b 的 null bug（2026-10-12 实测）

```
z6.b extends com.badlogic.gdx.utils.g0 (libGDX Pool)   ← 单例, 静态字段 a
z6.b.b()  = c().obtain() ; obj.d = false               ← obtain() 偶尔返回 null → 紧跟的 iput-boolean NPE
z6.b.c()  = 拿单例(没有就 new)
z6.b.e(x) = if (x.d != true) { x.d = true; c().free(x); } else throw EmptyStackException
z6.b.newObject() = new z6.a()
z6.a.d()  = z6.b.b()                                   ← "给我一个临时大数"
z6.a.w(o) = this.d() 后做减法                          ← r4.c.i() 的血量插值就用它
```

`obtain()` 只在 **free 列表里被塞进 null**（并发 add 导致 `Array.size` 虚高、尾部槽位是 null）时才返回 null。
触发条件：`r4.c.i(row)`（街区最大血量）在**伤害结算路径**里被调用 —— 也就是 `r4.i.l()` 内部。
铁长老 `getHitMod()=0` 时该路径不可达；**一旦旁路把 hitMod 拉成 1.0 就会踩到**。

**护栏**（`agent.js` 的 `installBigPoolGuard`）：

```js
ZB.b.implementation = function () {          // ZB = Java.use('z6.b')
    depth++;
    try {
        if (depth > 1) return ZA.$new();     // ⚠ 本环境 this.x() 会再进替换体, 必须用深度判定
        var r = this.b();
        if (r === null) return ZA.$new();    // 池吐 null → 兜底新建(构造后 d 默认 false, 语义一致)
        return r;
    } finally { depth--; }
};
```
